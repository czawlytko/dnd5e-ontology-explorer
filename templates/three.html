    How the two files were merged

    An ontology is a set of triples, so merging two ontologies is a union: pour every triple from both files into one graph. Nothing needs matching by hand. Wherever the files use the same IRI, they automatically connect at that node. Where the IRIs differ, even by one letter, the two stay separate.

    The D&D file was written against TTRpg's namespace, so most of it lines up. Weapon, Armor and Currency now sit under TTRpg's Item Type, which gives 56 D&D items a parent they lacked before. Character and Location were only references in the D&D file and now have real definitions. TTRpg also adds the game-level ideas the D&D file never mentions: Player, Campaign, World, Item and Action.

    The two triples found in both files are the author's name and email, which each file repeats. Duplicates are harmless in a union, because the same triple only counts once.

    What didn't line up

    Tools vs. Tool Doesn't join

    The D&D file hangs its 123 tools on TTRpg:Tools, but TTRpg defines TTRpg:Tool. Because of one letter, they're two unrelated nodes. Tools has no parent, and Tool has no children.

    Fix: rename to TTRpg:Tool in the D&D file, or add one bridging triple (see options below).

    Item Enhancement Not defined

    The D&D file uses TTRpg:ItemEnhancement as a parent for 3 classes, but TTRpg.ttl has no such class.

    Fix: define it in the D&D file's own namespace (DnD5eCharacter:ItemEnhancement), or ask TTRpg to add it.

    TTRpg's “type” property, defined three times Same-IRI merge

    TTRpg:type is declared three times, for characters, items and spells. That's the Divination problem again, this time on a property. Once loaded, it has 3 domains and 3 ranges. In RDFS, multiple domains all apply at once, so the merged file says anything with a type is a Character and an Item and a Spell. The original pairing is lost, and the graph shows all 9 combinations.

    Fix: three properties (characterType, itemType, spellType). TTRpg:existsIn has the same issue with Item and Spell.

    Small typos that change meaning Quiet errors

    The D&D file defines its alignment class as Alignemnt, but the 9 alignments point to Alignment, which is never defined. DraconicAncestry is used as a parent 9 times and never defined either. In TTRpg.ttl, line 215 says owl:invereOf, so the link between existsIn and hasItem is silently dropped.

    Ways to merge for real

    This page merges the files in memory each time it loads, which is fine for exploring. For anything your team relies on, these are the usual approaches. They combine well.

    A · what this page does

    Load both and take the union

    Keep the files as they are and read both into one graph whenever you need them. Tools like Python's rdflib do this in two lines.

    Good: no edits, always current. Watch out: every tool and person has to know to load both files.
    B · recommended

    Declare an import

    Add one triple to the D&D file saying it imports TTRpg. Ontology editors such as Protégé and reasoners then fetch TTRpg automatically.

    DnD5eCharacter:Ontology
  owl:imports <https://w3id.org/TTRpg> .
    Good: the standard way to say “this extends that”. The D&D file uses TTRpg terms today without declaring it.
    C · recommended with B

    Add an alignment file

    A small third file of bridging triples that fixes mismatches without editing either source.

    TTRpg:Tools owl:equivalentClass TTRpg:Tool .
DnD5eCharacter:Alignemnt
  owl:equivalentClass DnD5eCharacter:Alignment .
    Good: you can fix things in files you don't own. Watch out: equivalentClass only takes effect in tools that apply OWL reasoning.
    D

    Write one merged file

    Save the union as a single new .ttl and share that.

    Good: simplest to hand around. Watch out: it's a copy that drifts from the originals when they're updated, and you lose track of which file each fact came from.

    Whichever you choose, keep track of provenance, meaning which file each triple came from. This page does that, which is how it can color dots by file. In RDF the standard tool for this is a named graph: each source file is loaded into its own labelled graph inside the same database.

    Why does Divination have two parents?

    It's an accident in the D&D file. In an ontology, each thing is identified by an IRI, a web-address-style name. If two things share an IRI, the ontology treats them as one thing.

    D&D uses “Divination” for a school of magic and for a spell in that school. The file gives both the same IRI:

    Line 1843 · the school 
    DnD5eCharacter:Divination a rdfs:Class ;
  rdfs:subClassOf
    DnD5eCharacter:MagicSchool .
    Line 2373 · the spell 
    DnD5eCharacter:Divination a rdfs:Class ;
  rdfs:subClassOf TTRpg:Spell ;
  DnD5eCharacter:inMagicSchool
    DnD5eCharacter:Divination .

    When loaded, all of these statements land on one node:

    There is one thing called Divination. It is a kind of Magic School and a kind of Spell, it belongs to the school Divination (itself), and 28 other spells belong to it.

    Shield has the same problem: the armor (line 1289) and the spell (line 3417) share one IRI. Both are red in the 3D view. The fix is to give each its own IRI, such as DivinationSchool and DivinationSpell. The label can still say “Divination” for both.

    When multiple parents are on purpose

    Having several parents, called multiple inheritance, is allowed. The D&D file uses it on purpose for 54 classes.

    Red Dragon

    Red Dragon is a Subrace (a red-dragon Dragonborn), a Draconic Ancestry (your breath weapon) and a Draconic Bloodline (a sorcerer origin). It's one idea that fits all three roles.

    Defense

    Defense is a fighting style that fighters, rangers and paladins can all pick, so it has four parents. All of them are correct.
